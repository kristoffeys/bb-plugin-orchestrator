Executive summary · Let Claude Cook

More control is already in the SDK.

BB Orchestrator already has the hard foundation: durable state, managed workers, routing, retries, and policy gates. The strongest next features come from making the BB host data it already has access to more visible and actionable.

Top three moves

high value with bounded implementation

Completion evidence bundle

Attach timeline, output, context, storage files, and diff evidence to every completion record. Reviewers can verify results without opening each worker thread.

One-click recovery

Turn a failed or bloated workstream into a guided choice: retry the turn, compact context, fork from the last healthy point, or clear context and resume.

Run sections

Create a BB thread section per run and keep coordinator and worker threads grouped automatically. This makes the existing visible-thread model easier to navigate.

Untapped capabilities

grouped under the BB host API
1. Thread lifecycle, waiting, and recovery

The plugin polls threads.get during provisioning and reacts to coarse lifecycle events. BB also exposes direct wait and recovery primitives.

  • threads.wait, threads.events.wait, threads.listRunning, threads.childSummary
  • threads.compact, threads.fork, threads.clearContext, threads.cancelPlan, threads.clearGoal
  • threads.conversationOutline, threads.output, threads.context, threads.timeline, threads.timelineTurnSummaryDetails
2. Pending work and message queues
  • Workspace view: threads.queue.list
  • Per-thread operations: threads.queuedMessages.create, list, update, reorder, send, delete, setGroupBoundary

These can expose and actively manage the work that is waiting behind an active worker.

3. Pending worker interactions
  • threads.interactions.list, get, respond, resolve, cancel

Orchestrator currently has its own coordinator input gate, but it does not aggregate provider/tool permission prompts raised inside workers.

4. Thread organization and navigation
  • threadSections.create, list, update, delete
  • threads.pin, unpin, reorderPinned, markRead, markUnread, open, tabs.get, tabs.update
5. Search, history, and reusable prompts
  • threads.search, threads.promptHistory, projects.promptHistory, threads.conversationOutline

These endpoints can turn archived work into an operational knowledge base and support replayable run templates.

6. Project-aware execution context
  • projects.defaultExecutionOptions, branches, commands, files, fileContent, paths, get
  • threads.defaultExecutionOptions, threads.resolveMentions

The current dispatcher accepts explicit routing but does not preflight project commands, branches, or default execution settings.

7. Environment changes and pull requests
  • Evidence: environments.status, diff, diffFiles, diffFile, diffPatch, diffBranches, paths
  • Lifecycle: get, list, listProviders, update, archiveThreads, delete
  • VCS actions: commit, pullRequest, markPullRequestDraft, markPullRequestReady, mergePullRequest
8. Host and provider readiness
  • hosts.list, get, directory, pathsExist, providerCliStatus, experimental_listProviders
  • hosts.installProviderCli, retryUpdate, experimental_resume, experimental_suspend

These can keep routing from selecting a host whose provider CLI, path, or machine state is unavailable.

9. System usage and execution limits
  • system.usageLimits, providerStates, executionOptions, attention, status.get

Current token budgets are based on observed run usage. Host limit and provider state data can prevent a run from starting on an exhausted route.

10. Files, artifacts, and previews
  • threads.storageFiles, storageLocation, storagePaths
  • files.read, write, list, listPaths, mkdir, move, remove, createPreview
11. Headless and integration surfaces
  • bb.cli.register for scriptable run start/status/cancel
  • bb.http.route for authenticated status and automation endpoints
  • bb.background.service for persistent reconciliation instead of cron-only sweeps
12. Dispatch control hooks
  • bb.experimental_hooks.on("message.dispatch", ...) and bb.experimental_hooks.recheck

The hook can hold or refuse dispatch attempts centrally, allowing Orchestrator's lane and budget policies to apply before provider work begins.

13. Settings, status, and discovery
  • bb.settings.define, bb.status.needsConfiguration, bb.ui.registerMentionProvider

Policy is currently stored through custom RPC and KV. Declarative settings and status can surface configuration health in BB's native plugin management UI; a mention provider can expose runs and artifacts in composers.

14. Native app UI components

The current app uses custom selects and dialogs. The public app contract also offers composer customization, thread/header/panel actions, command palette actions, homepage sections, fixed tabs, native provider/model and permission pickers, file links, and diff/source renderers. Several remain experimental in the current contract and should be gated by the declared SDK engine range.

Research notes and sources

primary sources

The inventory was produced from four code searches: package/SDK imports; hard-coded URLs and environment secrets; HTTP clients, OAuth, and webhooks; and every bb.* call site. A final pass inspected the installed SDK declaration surface and the full non-dependency repository file list.

  • Official BB Plugin SDK README — public contract, testing harness, composer, file preview, and extension capabilities.
  • Official backend contract source — authoritative host and SDK method definitions; the local installed 0.4.87 declarations were used for endpoint names.
  • Official app contract source — frontend slots, actions, native components, and navigation surfaces.
  • Official experimental API audit — maturity and stabilization notes for newer SDK surfaces.
  • Official BB changelog — recent plugin SDK and provider capability changes.
  • Official BB configuration guide — plugin storage, installation, compatibility, and trust model.

Scope guard. Experimental endpoints are opportunities, not commitments. Before implementation, keep the plugin's engines.bbPluginSdk constraint aligned with the exact contract used and provide a stable fallback for UI-only enhancements.
